## Approved identity policy

| Project type | External ID | Approved initial high-water mark | Next ID with no higher live value |
| --- | --- | ---: | --- |
| home | `PA` + number padded to at least four digits | 209 | `PA0210` |
| vehicle | `PB` + number padded to at least four digits | 82 | `PB0083` |
| repeating | `PC` + number padded to at least four digits | 8 | `PC0009` |
| misc | `PD` + number padded to at least four digits | 4 | `PD0005` |

UUIDs remain the primary keys and are generated by PostgreSQL. External IDs are
separate stable identities, unique within each raw table. Existing rows are not
updated or renumbered. Higher numbers currently present in the database raise
the initial high-water mark above the approved floor.

The owner accepts that numbers issued and deleted before initialization may be
unknown. Visible gaps are never filled automatically. After initialization,
deletion and failed inserts do not rewind an allocator. Recycle is an ordinary
new repeating project, not a replacement: it does not reuse `PC0003`. There is
no restore RPC, arbitrary-ID input, or historical-ID reuse workflow.

Padding expands after 9999 (`PD10000`); it never truncates. Sequences are bigint,
noncycling, and allocation eventually fails explicitly at bigint exhaustion.

## RPC behavior and concurrency

The browser supplies the selected type and the existing mapped project fields.
It supplies neither identity. A fixed allowlist selects the raw table and
per-type writable fields. Caller-supplied `id`, `external_id`, unknown fields,
invalid types, empty titles, and repeating projects without recurrence are
rejected. PostgreSQL generates the UUID, calls the type's sequence, inserts into
the corresponding table, and returns the inserted row as JSON in one RPC.
Omitted columns retain their database defaults.

`nextval` is PostgreSQL's atomic, multi-session allocation primitive; there is no
runtime `max + 1`, preflight availability race, or automatic insert retry.
Per-table unique constraints are the final duplicate guard. Allocation order is
monotonic; concurrent transaction commit order need not be. Failed transactions
can consume numbers, intentionally leaving gaps. An HTTP timeout can leave an
uncertain committed result: refresh and inspect before manually retrying.

The RPC uses `SECURITY INVOKER`, with an empty search path and qualified table
names. Existing table privileges, RLS, checks, defaults, and triggers still apply
to both insertion and returned-row access. It grants RPC execution and sequence
USAGE to `anon` and `authenticated`, matching the current browser-client roles;
it does not grant table access or relax policies. Sequence UPDATE is not granted,
so these roles cannot reset counters. They can consume sequence numbers, which
can create harmless gaps. Existing direct-table write grants are not revoked:
other authorized writers must coordinate with these allocators. A direct insert
choosing a future external ID can cause a later allocator insert to fail unique
validation; no silent recovery or renumbering is attempted.

Existing non-null external IDs with unexpected formats, oversized numbers, or
duplicates abort the proposed migration without rewriting project rows. Existing
nullable external IDs remain nullable and unchanged; every RPC-created row has a
non-null external ID, including home rows that require one.
The reviewed RPC also rejects orders outside int32 because the unified view
casts raw bigint orders to integer.

## Explicit repeating control: historical evidence and modern equivalent

Git commit `9b76e46` (original Add Project feature) establishes the original
behavior, independently of the retained edit-only `addToRepeating` field:

- Historical `www/screens/projects/projects.js`, `handleRepeatingCheckbox`
  and `renderAddProjectDynamicFields`, read the boolean, re-rendered the form
  and showed the recurrence selector only when checked. Validation required
  recurrence when `addToRepeating` was true.
- Historical `www/js/services/projects.service.js`, `createProject`, checked
  `payload.addToRepeating` before vehicle/home routing. It selected the repeating
  destination and called creation once: it did not create both a normal project
  and a repeating copy.
- Commit `591d7e7` (type-specific ID restructuring) and the last retained
  Workbench implementation at `f416bec^` kept that override. Workbench also
  allowed an explicit `repeating` source. Its checkbox revealed/removed
  recurrence and required it before submission.
- The modern form omitted the checkbox, offered all four types in the source
  dropdown and always showed recurrence. Its service correctly required an
  explicit repeating type: merely choosing weekly never selected that type.

Restoring the boolean is therefore semantically correct, not a new
recurrence-implies-type heuristic. The modern UI deliberately provides only one
repeating selector (the checkbox), rather than two competing type controls.
It retains the existing modern recurrence options and the database allocator.
It does not restore any legacy persistence, scheduling, fallback or conversion.
Existing edit controls and restrictions are unchanged.

The [editor regressions](../tests/workbench-project-editor.test.cjs) execute
transformed JSX event handlers, the real Workbench service and real data access
with a mocked RPC. A disposable PGlite integration additionally executes the
canonical RPC against the saved live schema/view as `anon`, confirming that
checking the box inserts only into `projects_repeating`, survives through
`projects_all` and retains recurrence. These tests never contact Supabase.
